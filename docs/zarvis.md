# Zarvis

Optional public X research, its privacy boundaries, independent abuse controls and enablement prerequisites are documented in [Public X research](zarvis-x-research.md). It is disabled by default and supplements the selected answer provider.

Zarvis is the OpenZcash AI guide: `/zarvis`, the navigation entry, and a floating conversation on public workspace pages. The UI follows OpenZcash's light and dark themes. Answers follow the language of the question; the interface itself stays in English.

## Language selection (2026-09-28)

The interface is English by design (placeholder, starters, statuses, buttons, privacy text, the About page); it says so where it matters: the composer reads "Ask Zarvis about Zcash, in any language…" and the welcome screen states that Zarvis answers in Portuguese, Spanish, English and more. No string table or locale toggle exists, and page chrome is not translated. Only the deterministic answer texts, the provenance badge under an answer and the fallback notice are trilingual.

Answers follow the question. `src/lib/zarvis/language.ts` decides the answer language for every deterministic block with one detector: an explicit stored preference ("Responda em português" / "Answer in English" / "Responde en español") wins; otherwise the latest user turn whose words score a strict majority for one language: function words count 2 (como, onde, quais, são, que, de/do/da, um/uma, o/a/os/as, para, com, não, e, em, … versus cuál, cuánto, es, son, el/la/los/las, del, y, hay, tiene, … versus what, how, the, is, and, in, on, at, from, …) and the few domain nouns the direct templates accept count 1 (saldo, dados, tesouraria, chave, … versus precio, cotización, tesorería, billetera, subvenciones, … versus price, treasury, balance, grants, viewing key, …), so "Como funciona a viewing key?" and "Qual o treasury balance da ZCG?" are Portuguese, "¿Cuál es el precio del ZEC?" and "Cotización del ZEC" are Spanish, and "a viewing key" is English. Accents and the Spanish ¿¡ marks are stripped before scoring, so "Cual es el precio del ZEC" scores the same. Everyday Portuguese that is also Spanish (se, vale, usa, pago, use, usar, sobre, por, dólares) counts for both, so "Como se usa uma viewing key?", "Vale a pena minerar Zcash?" and "Use dólares" stay Portuguese while "Usa dólares" and "Sé breve" stay Spanish. A tie between Portuguese and Spanish on shared words ("Saldo ZCG", "Última Arborist call") still goes to Portuguese, as before Spanish had templates, unless the raw text carries ¿, ¡ or ñ, which Portuguese never writes ("¿Último ZIP?" is Spanish); a tie between Spanish and French goes to Spanish; a tie that involves English ("Zashi on OS") is undecided; French alone is "other". Wordless and undecided turns such as "2025" or "ZIP 317" inherit the previous user turn's language; the default is English.

`AnswerLanguage` is `en | pt | es | other` and `DirectLanguage` is `en | pt | es`: every deterministic template (direct answers, reviewed FAQ text, calculator blocks, the Arborist and mining answers, the ledger facts and the grounding fallbacks on the model path) takes a `DirectLanguage` and reads its text through `pick(language, { en, pt, es })` from `language.ts`, which falls back to English for any template that lacks a translation, so an answer is never mixed-language. Numbers and dates use `locale(language)`: `en-US`, `pt-BR` and `es-419` (Latin-American Spanish, which keeps the dot decimal and comma grouping of the site's figures and prints "USD 1,234.50", "28 sept 2026, 11:36 a.m." and "hace 4 días"). A question in a language without templates ("other": French and everything else) has no direct route and goes to the model, whose instructions still say to reply in the user's language; its deterministic parts and badge are English. A stored `fr` preference disables the direct route entirely for the same reason; `en`, `pt` and `es` preferences keep it.

The Spanish phrasings the zero-cost direct route covers mirror the Portuguese ones (`direct-intent.ts`, `direct-faq.ts`; the paraphrase corpus in `direct-paraphrase.test.ts` holds the full list):

- courtesy: hola, buenas, hola Zarvis, gracias, muchas gracias;
- preferences: responde/contesta en español / en inglés / en portugués, usa dólares, sé breve, respuestas cortas;
- price: ¿cuál es el precio del ZEC?, cuánto vale un ZEC, cuánto cuesta el ZEC hoy, a cuánto está el ZEC, precio del ZEC, cotización del ZEC;
- treasury: saldo del ZCG, saldos del ZCG y del Lockbox, cuáles son los saldos actuales del ZCG, tesorería del ZCG, cuánto tiene / hay en el Lockbox, qué tiene el ZCG, de cuándo son los saldos, "… y qué tan actuales son los datos" and the follow-ups "¿y el Lockbox?", "¿y qué tan actuales son los datos?";
- mining: cuál es el hashrate (solrate) actual de Zcash / de la red Zcash;
- Arborist: cuál fue la última llamada / reunión Arborist, última Arborist call;
- ledger: cuánto pagó ZCG en 2025, cuánto ha pagado ZCG a Zingo, cuánto pagó ZCG a Zingo en 2025, cuánto pagó ZCG en grants / subvenciones, total pagado por ZCG, and the follow-up "¿y en 2025?" ("en grants" is optional in Spanish because the deterministic answer itself names the grant ledger and its exclusions);
- ZIPs: cuál es el último ZIP / el ZIP más reciente, qué es el ZIP 317, explica(me) el ZIP 317, cuál es el estado del ZIP 317, "¿y el ZIP 32?", "¿cuándo fue creado?";
- FAQ definitions: qué es Zcash / ZEC / ZCG / Zcash Community Grants / el Lockbox / una viewing key / una clave de visualización / una IVK / una FVK / una OVK / una dirección unificada / el halving / el Dev Fund / OpenZcash / Zarvis, also as "qué significa", "explica", "explícame", "háblame de(l)", "cuéntame sobre";
- FAQ questions: qué hace privada una transacción de Zcash, cómo funcionan las transacciones blindadas, cómo funciona la privacidad de Zcash, cuál es la diferencia entre transacciones transparentes y blindadas, qué puede revelar una IVK, puede una viewing key gastar mis ZEC, una IVK identifica al remitente, cuál es la oferta máxima de ZEC, cuánto es el 5% de 21 millones de ZEC, de dónde saca OpenZcash sus datos, cómo calcula OpenZcash los grants pagados, dónde está / cómo funciona la calculadora de tesorería, dónde encuentro carteras / billeteras de Zcash, qué es el hashrate, qué es un pool de minería, participar en un pool significa ser dueño de ZEC, dónde encuentro datos de minería de Zcash, por qué ZcashInfo y ZecStats muestran hashrates diferentes;
- fillers stripped before a second match: por favor, puedes, podrías, me puedes decir, quiero saber, me gustaría saber, dime, explícame, oye Zarvis, hola Zarvis, and anywhere: ahora, hoy, actualmente, en este momento, ahora mismo.

Qualified Spanish questions keep going to the model exactly as their English and Portuguese counterparts do ("¿Cuál era el precio del ZEC ayer?", "¿Es ZEC una buena inversión?", "¿Cuánto pagó ZCG a Zingo sin contar reembolsos?"), and an earlier Spanish instruction ("Responde solo en JSON", "Usa euros", "Responde siempre en español") keeps the conversation on the model.

## Provenance badges (2026-09-28)

Every `done` event carries `provenance`: `route` (`local` or `model`), `model` (the configured model id for model answers, `null` for direct answers), `webSearch` (a hosted search ran), `groundingFallback` (unsupported figures were replaced), `withheldFigures` (how many; never the text) and `language` (`en`/`pt`/`es`, the language of the deterministic parts; any other answer language is labelled `en`). Under each answer the chat renders one badge in the answer's language: "Direct from OpenZcash data · no AI" / "Direto dos dados OpenZcash · sem IA" / "Directo de los datos de OpenZcash · sin IA" for the zero-cost route, or "Grok 4.7 · 3 sources · check them" / "Grok 4.7 · 3 fontes · confira" / "Grok 4.7 · 3 fuentes · verifícalas" (plus "web search" / "busca na web" / "búsqueda web" when a search ran; "1 source" / "1 fonte" / "1 fuente" in the singular) for model answers; the model name comes from the done event's model id, falling back to the provider label from `GET /api/zarvis`. When a grounding fallback fired, a visible notice under the answer carries the count from `withheldFigures` ("2 figures could not be verified and were left out" / "1 valor não pôde ser verificado e foi omitido" / "3 cifras no pudieron verificarse y se omitieron"; "Some figures…" / "Alguns valores…" / "Algunas cifras…" when the count is unknown), so an answer whose sentences or table rows were dropped never reads as complete. Retrieval stamps in the sources drawer are printed in UTC. The badge labels the route, not the correctness of the answer; "Zarvis can make mistakes" still applies to both routes.

## Streaming, figure repair and Quick-mode research (2026-09-28)

**Streaming.** A model round streams `delta` events to the chat while it is written, unless figures must be checked first: a round is buffered when the evidence gathered so far is financial (`isFinancialEvidence`: quote, ledger, treasury, scenario or company data) or when the question itself is about money (`isFinancialQuestion` in `src/lib/zarvis/grounding.ts`: "how much" / "quanto", price, treasury, balances, grants, pay/paid/payment, funded/funding/funds, fees, rewards, salary, earn, sold/bought, USD, scenario, halving/subsidy words, a `$` or a "20x"), so a guessed preamble figure is never shown before the tools answer. xAI's private-use citation markers are withheld until they close and never streamed. The final `replace` is always authoritative (rendered citations, the checked or repaired text) and always precedes `done`; an empty `replace` clears a streamed tool preamble before the next round. Stop keeps the partial streamed text and marks the message incomplete; the client sends it to the next turn with the interruption label. Buffered rounds show "Writing and checking the answer…" and then "Checking N figures against the sources…" before the replace.

**Guard facts.** `numericFacts(evidence, documents)` now includes, besides the typed tool evidence and the site's derived treasury arithmetic, the protocol constants (`PROTOCOL_FACTS`: 21 million ZEC, 1,050,000 ZEC, 5%, the per-block subsidy split of both eras, derived from `blockRewardsAt` just before and at NU7: 1.5625 / 0.125 / 0.1875 / 1.25 ZEC before NU7 and 0.52083333 / 0.04166666 / 0.06249999 / 0.41666668 ZEC since NU7 (ZIP 218), and its 8 / 12 / 20 / 80 / 25 / 100 percentages) and every currency, ZEC or percent figure present in the reviewed notes and documents selected for the answer (`local.documents`), typed by the unit the note states. Unitless numbers (75 seconds, 1,680,000 blocks, halving heights) are never checked because the guard only reads currency, ZEC and percent claims. A Brazilian-real figure in a note never vouches for a dollar claim.

**Guard tolerance.** A claim is read at its own precision: the fact must round to it (half a step either way). Only an unscaled, exact currency or ZEC figure may instead be an integer truncation of a cents/fraction value (up to one step above), so "$3,396,155" for 3,396,155.67, "144,333 ZEC" for 144,333.79 and "$1,592" for 1,592.80 pass, while a scaled or percent figure one step low is wrong, not truncated: "$3.3M" for 3.396M, "$140 million" for 140.86M, "$1 billion" for 1.99B and "37%" for 37.99% are rejected. Behind about / roughly / approximately / around / nearly / ~ / cerca de / aproximadamente the tolerance widens to three significant digits, again half a step either way ("about $141 million", "roughly $140,859,000"; "approximately $140 million" for 140.86M is still one step low). "$3.396M" and "$3.396 million" read as 3.396 million; an ambiguous "3.396"-style token keeps both readings so the one the evidence supports wins. Wrong figures stay rejected: "$3.5M" for 3.396M (with or without "about"), "roughly 40%" for 37.99%, invented totals. The facts are computed once per answer (`numericFacts`) and reused for every sentence check.

**Repair instead of fallback.** When figures are still unsupported after a round, the engine runs one extra tool-less round with a developer message listing only the unsupported strings ("These figures are not in the evidence: … restate the answer using only figures from the evidence, or say which figure is unavailable"), under the same output budget; the discarded draft is never logged or emitted. The repair is time-boxed inside the generation deadline (`repairBudgetMs` in `depth.ts`): it starts only with at least 15 seconds left and gets the remaining time minus a 5-second reserve, under a signal combined with the request's own, so a slow restatement expires into the fallback below instead of a "reached its time limit" error; with less time left the repair is skipped (`repairRounds` stays 0) and the fallback applies at once. Only the request's own abort (Stop or the deadline itself) propagates out of the repair. If figures remain unsupported afterwards, the sentences containing them are dropped and the verified sentences are kept whenever at least one sentence with a figure or a date survives; otherwise the previous fallback applies (computed ledger facts and comparison, or the "could not validate" text). `provenance.withheldFigures` carries the count. Repair rounds are counted as `repairRounds` in the process metrics and in the `zarvis.chat` log line; a failed repair round leaves the request unpriced (`usageReported: false`).

**Quick-mode research.** Tools stay available in every round except the true final synthesis round. A granted `request_external_research` adds one bounded round (Quick 3 → 4, Deep 4 → 5, `roundBudget` in `depth.ts`) because the request consumed one, so lookup → request → search → synthesis fits in Quick within the unchanged 55-second deadline. Without a granted request Quick stays at three rounds.

**Grok search domains.** xAI accepts at most five allowed domains per search, so `researchScope()` picks the list by topic (`GROK_SEARCH_DOMAINS` in `provider.ts`): general → openzcash.org, zechub.wiki, z.cash, zips.z.cash, forum.zcashcommunity.com; governance/funding (ZCG, grants, treasury, Lockbox, Dev Fund, votes, NU upgrades, proposals, ZF/ECC) → openzcash.org, forum.zcashcommunity.com, zfnd.org, electriccoin.co, z.cash; news/releases → electriccoin.co, zfnd.org, forum.zcashcommunity.com, z.cash, openzcash.org; mining → zcashinfo.com, zecstats.com, zips.z.cash, z.cash, electriccoin.co; history → openzcash.org, z.cash, electriccoin.co, shieldedlabs.net, zfnd.org; ZIP questions → zips.z.cash only. OpenAI receives the whole reviewed list. Every domain is in `SEARCH_DOMAINS`, so citations stay allowlisted.

## Enable

1. Create a **dedicated OpenAI project and restricted API key** for OpenZcash. Allow the Responses API and the selected model. Save the key as `OPENAI_API_KEY` in the server's secret manager (the Railway service's variables), never in client code or a `NEXT_PUBLIC_` variable. Do not paste it into chat or commit it.
2. Apply the additive `0005_zarvis_usage` migration through the existing boot migration process. It creates only short-lived request counters, not a conversation table. Requests fail closed if the table/database is unavailable.
3. Set `ZARVIS_ENABLED=true`. The defaults are `ZARVIS_MODEL=gpt-5-mini`, `ZARVIS_WEB_SEARCH=true`, `ZARVIS_DAILY_REQUEST_LIMIT=100`, and `ZARVIS_HOURLY_REQUEST_LIMIT=30`. The production request origin is pinned to `https://openzcash.org`; set `ZARVIS_ORIGIN` explicitly for a preview domain or a local listener whose internal hostname differs from the browser URL. Forwarded host headers cannot expand this allowlist. Set `ZARVIS_ENABLED=false` to turn off paid calls immediately. The feature stays disabled by default until deliberately enabled.
4. Test a basic privacy explanation, a current treasury query, an external protocol question, and a Portuguese follow-up. Check citations, reporting dates, source failures, light/dark modes and mobile. A rendered UI or configured key is not proof that a billed model call succeeded.
5. Set a project budget alert and appropriate billing controls in OpenAI. **App request limits are not a dollar billing cap.** Inspect actual usage before raising them.

## Local testing without request quotas

Set `ZARVIS_LOCAL_UNLIMITED=true` in the local development environment when deliberately testing without hourly, daily or per-network question limits. This setting only takes effect with `NODE_ENV=development` and an explicit HTTP loopback `ZARVIS_ORIGIN` (`127.0.0.1`, `localhost` or `::1`). This local flag never changes production quotas. The flag is false by default.

This mode does not read, increment or reset the quota counters, so an exhausted test counter no longer blocks the preview. Disable the flag to resume ordinary quotas. The origin checks, input limits, per-answer output budget, deadline and stop/cancel behavior still apply. Model-assisted answers continue to use the configured provider and incur its normal API costs. Deterministic local answers make no model call. All submitted questions count toward request quotas unless local testing or the explicit launch window below is active.

## Temporary launch window

Set the server-only `ZARVIS_QUOTA_PAUSE_UNTIL` to an explicit UTC expiry such as `2026-09-29T03:00:00.000Z` (midnight ending September 28 in Sao Paulo). The override is active only during the final 24 hours before that instant. Omitted, malformed, timezone-less, expired or more distant values keep normal quotas. The server rechecks the clock for every request; at expiry it automatically resumes the configured global quotas and ordinary network quotas without a restart or scheduled job. Clear the variable to end the window early.

During this window, global hourly/daily and per-network question counters are bypassed without reading, incrementing or resetting them. Existing counters remain intact for normal enforcement afterward. Accepted in-flight answers can finish under their existing deadline. The feature enable switch, origin/body checks, per-process concurrency, token/tool budgets and deadlines still apply. Model-assisted answers incur normal provider costs; there is no request-count cap during the window; the hard cap during a pause is the estimated-spend ceiling `ZARVIS_DAILY_USD_CAP` (see Operations), which is checked before the pause exemption and is set in production. Direct answers still make no model call.

The former admin `GET /api/zarvis/metrics` route is retired with the login and returns 404. Public readiness does not disclose quota settings.

## OpenZcash first (2026-09-27)

1. `scripts/build-zarvis-knowledge.mjs` extracts visible public text from an explicit allowlist of 54 source files. The generated index currently contains 109 chunks. `predev` and `prebuild` regenerate it; `npm test` checks it matches its sources. No repository crawl, private routes, environment files or code execution is involved. Rebuilding covers published local edits, not arbitrary changes on external websites.
2. A bilingual lexical search selects at most four documents within a 5,000-character budget. Short continuations can use the preceding exchange; a new subject searches for itself. Curated notes and selected navigation accompany the public page excerpts; the whole website is never injected into every prompt.
3. Supported factual questions use deterministic replies with zero model calls: USD prices; ZCG/Lockbox reported or estimated holdings; annual/all-time ZCG and coinholder paid-grant aggregates with optional explicit project fragments; reviewed EN/PT basics and site links; and exact numbered ZIP metadata with an official abstract excerpt. Plain latest-ZIP questions use the fresh complete catalog's Created ordering. Known continuations such as “e em 2025?”, “e o Lockbox?” and “and ZIP 32?” retain their specific scope. Unknown prior instructions, extra requirements and ambiguous continuations go through synthesis. See [direct-answer coverage and evaluation](zarvis-direct-answers.md) for limits.
4. Other requests get relevant public evidence before synthesis when the topic is clear. `query_openzcash_ledger` computes totals over the complete selected dataset by program, calendar year and optional literal name fragment. It preserves negative returns, excludes test entries, reports missing currency values and uses payment dates. It never totals excerpts. Program scopes are separate; USD budget values of paid entries are not bank settlements or today's ZEC valuation.
5. Questions outside those direct templates use the selected model with a stable instruction prefix, recent conversation and bounded evidence. Additional local lookups and `request_external_research` are available. ZIP questions first read the complete official local catalog; current external protocol/release questions without catalog evidence may start with web search enabled; otherwise the model must request it because local evidence is missing or too old. Lack of search access must be disclosed.

Ledger aggregate caches hold public totals for up to 60 seconds, use the import version and a hash of filters as the key, coalesce simultaneous reads, and retain at most 100 entries. They contain no chat history or generated answers. Existing quote/dashboard reader caches retain their original freshness semantics. A quote can be cached and fresh; a saved stale quote is never the deterministic current-price answer.

This is retrieval, not training or permanent model memory. It covers indexed public documentation and the wired data readers, not every linked PDF, full news article, future page or external website. Reports/records retain their publication, import and observation dates. The model still spends tokens reading evidence and writing explanations. No blanket percentage cost saving is guaranteed.

## Prepare or switch to Grok

The OpenAI configuration stays active until deliberately changed. To use Grok, set these server-side variables together:

```dotenv
ZARVIS_PROVIDER=xai
ZARVIS_MODEL=grok-4.7
XAI_API_KEY=<secret-manager-value>
```

OpenAI uses `ZARVIS_PROVIDER=openai`, `OPENAI_API_KEY` and the explicitly configured `ZARVIS_MODEL`. If no model is set, the defaults remain `gpt-5-mini` for OpenAI and `grok-4.7` for xAI. Missing Grok credentials do not silently fall back to OpenAI. Unknown providers disable the endpoint. Readiness and privacy copy follow the configured provider.

The adapter uses fixed provider hosts, the Responses API, `store: false`, bounded reasoning/output by response depth, no automatic retries and the shared app deadline described below. It requests `max_tool_calls: 2` with OpenAI and the documented `max_turns: 2` with xAI. Grok search receives at most five allowed primary/community domains, chosen by topic (see the search-domain list above), and no OpenAI-only verbosity setting. Encrypted reasoning is explicitly requested for both providers and forwarded unchanged within a stateless tool loop. Neither provider's requested hosted-tool limit is presented as a dollar cap. Grok has been contract-tested and exercised locally with real 4.6/4.7 responses; see the dated evaluation reports for results and limits.

Official integration references: [Grok 4.7](https://docs.x.ai/developers/grok-4-7), [Responses contract](https://docs.x.ai/developers/rest-api-reference/inference/responses), [web search](https://docs.x.ai/developers/tools/web-search), [xAI data policy](https://docs.x.ai/developers/faq/security), [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching).

## Switch to Claude (2026-10-07)

The same engine (`src/lib/zarvis/engine.ts`: local evidence first, function tools, optional hosted search, the numeric guard with its repair round, streaming) runs on either of two transports chosen by `ZARVIS_PROVIDER`: `src/lib/zarvis/responses.ts` for OpenAI and xAI (the Responses API, unchanged request for request) and `src/lib/zarvis/anthropic.ts` for Anthropic's Messages API through `@anthropic-ai/sdk` (pinned in `package.json`). To run on Claude, set these server-side variables together; nothing else changes:

```dotenv
ZARVIS_PROVIDER=anthropic
ANTHROPIC_API_KEY=<secret-manager-value>
ZARVIS_MODEL=claude-sonnet-5-5        # the default when unset
ZARVIS_FALLBACK_PROVIDER=xai          # optional: xai or openai, with its own key (XAI_API_KEY / OPENAI_API_KEY)
ZARVIS_FALLBACK_MODEL=grok-4.7        # optional: the fallback provider's default when unset
```

Readiness (`GET /api/zarvis` reports `"Anthropic (Claude)"`), the badge ("Claude Sonnet 5.5 · 2 sources · check them"), the about page ("called through its Messages API") and the privacy note follow the configured provider. Each provider reads only its own key; a missing key disables the endpoint rather than borrowing another provider's.

**Failover.** With `ZARVIS_FALLBACK_PROVIDER` set, a request whose *first* model call fails on the primary provider before any text was streamed, with class `provider_billing`, `provider_http_429`, `provider_http_5xx`, `provider_connection` or `provider_timeout`, runs its model part once more on the fallback (the local preparation is not repeated; the first call's failed attempt is not counted). Metrics, the `zarvis.chat` log line and the provenance badge report the provider and model actually used, and the `failover` alert names both providers and the class. Nothing fails over after the first call (tool state would be lost), after a delta reached the visitor, for a request-side class (4xx, incomplete, tool limit) or when the fallback itself fails: the fallback's own class is then reported. The fallback is a Responses provider (`xai` or `openai`); it needs its own key and must differ from the primary.

**What differs on Claude.**

- *Messages API.* No `store` flag exists; the request carries the system prompt, the tools and the whole turn list every time. The system prompt is the first `system` block with `cache_control: {"type": "ephemeral"}`, so the stable prefix (tool definitions + prompt) is cached and billed at the cache-read rate after the first request in five minutes; `cache_creation_input_tokens` and `cache_read_input_tokens` are counted into `inputTokens` and priced at the write and read rates. The LOCAL EVIDENCE block opens the first user turn (ahead of the visitor's first message) rather than a system block: the Messages API keeps data in user turns and instructions in `system`, so untrusted records never enter the instruction tier, and the cached prefix stays byte-stable. Application instructions that the Responses path sends as `developer` messages (final synthesis, figure repair, scenario note, computed comparison) are text blocks in the user turn prefixed `[OpenZcash engine instruction]`, after any `tool_result` blocks; one sentence appended to the system prompt (`ENGINE_INSTRUCTION_NOTE` in `prompt.ts`) explains the prefix. Thinking blocks, tool-use ids and `web_search_tool_result` blocks with their `encrypted_content` are echoed back exactly as returned, one assistant message per model turn. A thinking block is bound to the system prompt, the tool list and the messages before it (the API rejects a changed prefix on accounts created from 2026-08-31 and asks every integration to be append-only), so the request never edits what it sent: the tool list is fixed by the first round of a request, the synthesis and repair rounds send `tool_choice: {"type": "none"}` instead of a shorter list (`tool_choice` is outside the prefix check), and the local tools stay listed after the lookup cap, where an over-cap call gets the limit result as on every provider. A turn in which Claude calls the server search and a local tool together ends with `stop_reason: "tool_use"` and the search not yet run; the next user message then carries only the `tool_result` blocks (an engine note added for that round waits for the following turn), the tool list stays as it was and `tool_choice` is left unset so the API runs the search first; its result opens the next response. Visitor text that imitates the `[OpenZcash engine instruction]` marker is labelled `[visitor text]` before it is sent (`VISITOR_TEXT_LABEL`), so no history block can begin with the marker. Effort comes from the response depth as `output_config.effort` (`low` / `medium` / `high`) on every request; thinking stays at the model's adaptive default. The transport therefore targets the models the effort page lists (Sonnet 5.5, Haiku 5.5, Opus 5.5, Sonnet 4.6 and later); `claude-haiku-4-5` is in the rate table for pricing only. `max_tokens` is the depth's output budget plus `THINKING_HEADROOM` (8,000 tokens), because thinking counts toward it even with its text omitted and a higher `max_tokens` has no rate-limit cost; `stop_reason: "max_tokens"` is an incomplete response whose usage still reaches the failure's priced lower bound, `"refusal"` is text, and a `"pause_turn"` is continued (same tools, paused content re-sent as-is) up to three times inside the same round and time budget, its messages rendered as separate paragraphs.
- *Search.* The server tool `web_search_20260318` is called directly (`allowed_callers: ["direct"]`, no dynamic filtering) with `max_uses: 2` and `allowed_domains` set to the whole reviewed `SEARCH_DOMAINS` list for general questions and to the topic lists (ZIP catalog, mining, history, governance, news) otherwise; there is no five-domain cap. Because the tool list cannot grow during a request, the search tool is declared from the first round whenever `ZARVIS_WEB_SEARCH` is on, for every question: the `request_external_research` step of the Responses providers does not exist on Claude, the model decides under the same LOCAL EVIDENCE FIRST instructions, and `max_uses` bounds each model call (at most two searches per call, so a four-round answer can search at most eight times). Searches are counted from `usage.server_tool_use.web_search_requests` ($0.01 each). Citations of type `web_search_result_location` become sources and a markdown link after the cited text when their host is on the citation allowlist; the rest are dropped.
- *Page reading.* The server tool `web_fetch_20260318` (`anthropicFetchTool` in `anthropic.ts`) lets Claude read a page in full instead of relying on search snippets: `allowed_callers: ["direct"]` (no dynamic filtering, the same ZDR-eligible shape as the search tool), `max_uses: 2`, `max_content_tokens: 12000` (an approximate cap on the page text that enters the context; it does not apply to PDFs), `citations: {"enabled": true}` (off by default for fetch) and `allowed_domains` set to `SEARCH_DOMAINS`. Fetch filtering matches hosts only and an entry with a path never matches a fetched URL, so the GitHub organizations the citation allowlist accepts cannot be listed and a GitHub link is a citation but not a readable page (`fetchableSourceUrl` in `sources.ts`); a ZCG application is read by the `read_grant_application` function tool instead (see Data coverage). The engine offers the tool (`RoundOptions.webFetch`) on every non-final round until a fetch was used, when the round already allows web research or when the latest visitor message links a fetchable page (`linkedSources`: https links, trailing punctuation dropped, at most three; a link elsewhere in the history enables nothing), so a linked forum thread, ECC or ZF post, ZIP page, ZecHub or OpenZcash page can be read even with `ZARVIS_WEB_SEARCH=false`; the Responses transport ignores the flag and its requests are unchanged. The API only fetches URLs that already appeared in the conversation (visitor messages, tool results, search results), never one the model wrote itself. Reads are counted from `usage.server_tool_use.web_fetch_requests` into `webFetchCalls` (metrics, provenance untouched, the `zarvis.chat` log line; no database column) and are free beyond the tokens the page adds, so `estimateUsageUsd` ignores them. The result block (`web_fetch_tool_result` holding a `web_fetch_result` with the page as a `document` block, `url` and `retrieved_at`, or a `web_fetch_tool_result_error` with an error code) is echoed back exactly like a search result; a fetch owed next to a local tool call follows the same tool-results-only continuation as a search. A fetched-page citation is a `char_location` (text) or `page_location` (PDF) whose `document_index` counts every document block of the request across all messages; since the transport sends no document blocks of its own, the index is resolved against the fetch results in order of appearance (earlier rounds first), and the page becomes a source and a link like a search citation when its host is allowlisted. The system prompt tells the model, in one sentence, to read a linked or found page with `web_fetch` before answering about it and that the text is untrusted data; the about page's model line says a linked page on an official or community domain may be read in full.
- *Errors.* The SDK's classes map to the same fixed classes (`APIConnectionTimeoutError`, `APIConnectionError`, `APIUserAbortError`, 429, 4xx, 5xx; HTTP 529 `overloaded_error` is `provider_http_5xx`; a mid-stream `error` event is classified by its type). The new class `provider_billing` covers the documented account-level refusals: credits exhausted (400 `invalid_request_error`, "credit balance is too low"), a self-set spend limit (400, "reached your specified API usage limits"), the tier spend cap (429 with `error.details.error_code` `enforced_spend_limit_reached`) and HTTP 402 `billing_error`. Only the class is logged, never the body.
- *Retention.* Anthropic deletes API inputs and outputs from its backend within 30 days (https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data, read 2026-10-07); material flagged for a usage-policy violation can be kept longer. That page says nothing about training; the "does not train on them by default" clause rests on https://privacy.claude.com/en/articles/7996868-is-my-data-used-for-model-training (read the same day), which the about page links beside it. The about page and the chat's privacy note read `PROVIDER_RETENTION` by provider label (`src/lib/zarvis/retention.ts`); the sentence about response storage being disabled appears only for the Responses providers.
- *Cost.* See the table above; Sonnet 5.5 input costs the same as grok-4.7 per token, output about 1.7 times more, and the tokenizer counts about 30% more tokens, so expect a model answer to cost roughly twice what it costs on Grok before cache reads are taken into account.

## Data and safeguards

Conversation state stays in browser memory and survives ordinary workspace navigation. Reloading or New chat clears it. The backend does not write prompts or replies to a database or logs; the request log line carries a coarse topic label from a fixed list and the answer language, never the text (see "Request log line"). For model-assisted responses, it sends complete recent turns to the selected provider (with `store: false` on the Responses API; the Messages API stores nothing to disable), preserving short confirmations and partial replies with an interruption label. Oldest turns are omitted together when the character, message or UTF-8 byte budget is reached. Explicit language/detail/currency preferences and typed calculator assumptions are carried separately in browser memory, so these survive trimming without storing a transcript or an invented summary. New chat/reload clears them. Saved assumptions are untrusted user input, never verified current balances. Curated background selection considers both sides of the recent exchange, because a follow-up may refer to a subject introduced by the assistant. This does not exempt provider abuse-monitoring retention; the UI links to the provider's policy. Hosting access logs are separate.

A daily HMAC digest of the proxy-reported network address keys short-lived abuse counters. Raw addresses and messages are not persisted by this feature. Counters expire at the end of their windows and are removed on subsequent requests; they are not audience analytics or unique-person counts. Proxy-derived network quotas are advisory; atomic global caps remain effective even if headers are forged. No location or identifier is sent to the model provider as a search location / user identifier.

Chat and feedback JSON uploads have an absolute five-second read deadline and cancel on timeout or disconnect. The server enforces a 32 KiB chat request body, up to 40 recent messages / 18,000 characters, a 2,000-character question, at most three model rounds (four for deeper analysis), up to two automatic public lookups plus three model-requested local lookups (five for deeper analysis), two requested hosted-tool calls for OpenAI or two server-side rounds for xAI per model call (a round may contain multiple searches), 3,000 output tokens per model call (6,000 for deeper analysis), no automatic provider retries and a 55-second generation deadline (110 seconds for deeper analysis). Usage limits default to 5 requests per network per 10 minutes and 20 per day (`ZARVIS_NETWORK_WINDOW_LIMIT`, `ZARVIS_NETWORK_DAILY_LIMIT`), plus the global hourly/daily limits (`ZARVIS_HOURLY_REQUEST_LIMIT`, `ZARVIS_DAILY_REQUEST_LIMIT`) in Postgres; the global caps accept up to 1,000 per hour and 10,000 per day. Every question is charged to all four counters before generation; a completed **direct answer** (local route, zero model calls) hands the unit back (`refund` on the allowance: `greatest(count - 1, 0)` on the same keys, best effort), so only model answers and failed or aborted requests count against a visitor. Failed/aborted requests consume their reservation to prevent retry abuse. A request can still incur cost before cancellation. Source content and user-supplied instructions cannot grant access to additional tools.

The UI renders no model-generated HTML or images. No third-party model endpoints are exposed in browser CSP; calls and the API key stay server-side. The model cannot send transactions, access funds, execute scripts, contact others or modify records.

Rerun it when an answer should cite a post newer than `externalRetrievedAt`, typically together with the Monthly and ZIP syncs before a release, and commit the JSON; chat requests never fetch these sites.
- **Refresh:** `npm run knowledge:sync:zips` imports only numbered/draft `.rst`/`.md` files from `zcash/zips`, plus its README and license, at one pinned commit. Four parallel readers, source size limits, Git blob integrity, completeness checks and an atomic write protect the last complete snapshot. `npm run knowledge:sync` also updates explicitly published PDF text (Python 3 and Poppler required for PDFs). Website text rebuilds during normal builds. The runtime ZIP cache revalidates on demand after six hours, coalescing requests: unchanged revisions need one GitHub metadata call; changed revisions need the tree and at most 12 changed public files within an eight-second deadline. Larger changes require an offline sync. No AI search, credential or conversation is sent to GitHub. A failed refresh preserves dated evidence, marks it stale and backs off for one minute. This cache is per process and resets on restart, not a background scheduler. Publication, creation, revision and network activation remain distinct.

- **Treasury tool:** calls the same pure engines as the calculator, including halvings, supply denominator, fixed miner share, one future purchase, dev-fund continuation and community budget coverage. Default horizon is one year; default company balance is the documented August 31 record; default annual budget is cumulative milestones divided by five assumed years. Defaults and dates are stated. Each calculation reads public snapshots again; the returned link freezes the exact numerical inputs for reproduction. The tool supports company, community or both. Scenario responses use deterministic Portuguese/English templates, rather than model-generated monetary arithmetic.
- **Source outages:** supported USD quote, treasury and paid-grant questions return dated cached data or an unavailable response locally. They never interpret a missing record as zero or pay a model merely to explain a feed outage. Qualified/conversational questions retain model reasoning and source checks.
- **Financial checks:** monetary/ZEC/percentage figures in model answers based on financial tools are matched against their typed numeric evidence, including computed same-scope ledger year comparisons, for treasury evidence the site's own derived figures (per-pool and combined valuations at the quote, ZEC totals, shares of supply and the ZIP 1015 subsidy split), the protocol constants and the figures stated in the reviewed notes selected for the answer, with truncation, rounding and "about" tolerances (see the streaming and repair section above). Unsupported figures trigger one repair round, then sentence-level withholding or the grounded fallback. Output stays buffered while this check applies. This is a numeric/unit check, **not** universal semantic entailment, an audit of the source records, or proof that every claim in an answer is correct.
- **Session:** scenario changes merge into typed previous assumptions; an explicit future price replaces a multiple and vice versa. Preferences are data, not instructions elevated above system rules. Large histories still have a bounded recent-turn window; arbitrary old details are not permanent memory.

## Operations and feedback

`ZARVIS_MAX_CONCURRENT` defaults to eight active generations per server process (bounded to 32). Excess requests receive 429/Retry-After before a model call. This also applies during unlimited local testing and a temporary launch window. Outside those explicit exceptions, atomic global request quotas in Postgres remain the cross-replica cost/abuse safeguard; per-process concurrency is not a global dollar cap.

The former admin `GET /api/zarvis/metrics` endpoint is retired. Process counters, durable daily metrics, feedback reasons and alerts still collect internally. Set `ZARVIS_AGGREGATE_METRICS=true` to print aggregate process counters at most once a minute when traffic arrives. No prompt, reply, credential, raw IP or visitor identifier is added to these metrics. Hosting logs are separate.

Cost estimates use the built-in rate table above for the active model; the `ZARVIS_*_USD_PER_MILLION` / `ZARVIS_SEARCH_USD_PER_CALL` variables override single fields. An unlisted model without overrides, or usage missing from any model round, means **unpriced**, never zero; with `ZARVIS_DAILY_USD_CAP` set, an unpriced model answer sends the `unpriced_usage` alert because the cap cannot count it. Estimates are not provider invoices; failed/aborted requests are counted from the usage reported before the failure and may incur further unreported charges. `ZARVIS_DAILY_USD_CAP` is an application ceiling on the estimate, not a replacement for the provider's billing controls.

Answer feedback sends only a signed one-hour ticket, a useful/needs-work vote and, with a needs-work vote, an optional reason id from the fixed list in `src/lib/zarvis/feedback.ts` (wrong_figure, outdated, missing_source, off_question, wrong_language, unclear, other; the chat shows them as chips after “Needs work”, with Skip). Reasons are counted per UTC day and route in `zarvis_feedback_reasons` (migration `0007_zarvis_feedback_reasons`, flushed in the same transaction as the daily counters); a reason with a useful vote, an unknown reason or any extra field is rejected with 400. Tickets contain a random nonce/expiry and the answer route (`local` or `model`, so votes can be attributed per route in the daily table), no question, answer, identity or scenario. Votes are deduplicated per process with bounded memory; counters are directional feedback, not an authenticated survey. The backend rejects arbitrary feedback text. Calculator links contain public numerical assumptions, not chat text.

## Observability and operations (2026-09-28)

Everything in this section records counts, labels, durations and money. No question, answer, prompt, provider error body, raw IP or visitor identifier is logged or stored. The only thing said about a question is a coarse topic label chosen from a fixed list of fifteen subjects.

### Request log line

`POST /api/zarvis` prints exactly one single-line JSON record per request through `console.info` (visible in the Railway deploy logs, `event` = `zarvis.chat`):

```json
{"event":"zarvis.chat","at":"2026-09-28T19:02:11.512Z","route":"model","outcome":"completed","depth":"quick","ms":6120,"modelCalls":2,"webSearchCalls":1,"inputTokens":18320,"cachedInputTokens":9216,"outputTokens":640,"groundingFallbacks":0,"repairRounds":0,"estimatedUsd":0.0301,"errorClass":null,"topic":"wallets","lang":"en"}
```

- `route`: `local` (deterministic answer, no model call), `model`, or `rejected` (the request never reached generation).
- `outcome`: `completed`, `failed`, `aborted` (client disconnected), `quota` (Postgres request limit), `busy` (per-process concurrency), `spend_cap` (daily USD ceiling), `storage` (quota table unavailable), `forbidden` (origin), `invalid` (body), `disabled`.
- `errorClass` is a fixed label from `src/lib/zarvis/errors.ts`: `provider_timeout`, `provider_connection`, `provider_http_429`, `provider_http_4xx`, `provider_http_5xx`, `provider_not_configured`, `incomplete_response`, `empty_response`, `tool_limit`, `public_read_timeout`, `model_required`, `deadline` (the app's own generation deadline), `aborted`, `unknown`. Failures are classified inside the answer pipeline (`GenerationFailure`), which also carries the token usage billed before the failure so it is counted.
- `repairRounds`: tool-less rounds spent restating unsupported figures (0 or 1); `groundingFallbacks` counts answers where figures were still withheld afterwards.
- `topic` (2026-10-08) is one label from the fixed taxonomy in `src/lib/zarvis/topics.ts`: `price`, `treasuries`, `grants-ledger` (ZCG payments, proposals and grantees), `coinholder-grants`, `governance` (committee, elections, meetings, votes, Dev Fund), `zips-protocol` (ZIPs, network upgrades, halving, issuance, Arborist calls), `wallets`, `privacy-keys`, `mining-network` (hashrate, difficulty, chain data), `communities`, `news-forum`, `calculator-scenario`, `history-people`, `site-help` (OpenZcash, Zarvis itself, data sources) or `other`. `conversationTopic()` asks the direct routes first (a follow-up such as "and the lockbox" inherits the subject it continues), then the strong markers (a ZIP number, a forum link, a historical question) and then compact per-topic term lists in English, Portuguese and Spanish, scored by distinct matched words with the answer language counting double on a tie. It is deterministic, costs microseconds and never returns a word of the question; `src/lib/zarvis/topics-classify.test.ts` holds the labelled set it is checked against. `lang` is the language label the pipeline stamped on the `done` event (`en`, `pt` or `es`; any other answer language is labelled `en`, as on the badge); a failure before `done` is labelled from the question's own words. Both are `null` on a `rejected` line.
- `estimatedUsd` is `0` for local answers and `null` when nothing could be priced (unlisted model, or a completed answer with a missing usage report). A `failed`/`aborted` line carries the lower bound priced from the usage reported before the failure.

Rejections are rate limited in the log: the first rejection per outcome in a ten-second window is printed as above, and any further ones in that window fold into one `zarvis.rejections` line (`outcome`, `count`, `windowMs`, `avgMs`), so a flood of forbidden or busy requests cannot push the answer lines past the hosting log rate limit.

`python3 scripts/zarvis-topics.py` reads those lines from stdin (`railway logs --lines 5000 | python3 scripts/zarvis-topics.py`, optionally `--since 2026-10-01 --until 2026-10-07` on the UTC `at` field, `--json` for the raw report) and prints, per topic: count, share of the labelled questions, direct versus model share, failed answers and the median latency of completed answers, plus the language counts; lines written before topic logging are reported as unlabelled. Standard library only, no question text in or out; `src/lib/zarvis/topics-report.test.ts` runs it on `src/lib/zarvis/fixtures/zarvis-topics-log.txt`. The point is to see which subjects still pay for a model answer most often and give those a direct route next.

The canary prints one `zarvis.canary` line per run (`ok`, `ms`, `passed`, `failed`, `skipped`, `failedCases`, `skippedCases`, `stored`).

### Durable daily counters

Migration `0006_zarvis_observability` adds `zarvis_metrics_daily` (primary key `day` UTC date + `route`) and `zarvis_canary`. It is applied by the existing boot migration step (`scripts/migrate.mjs` in the Railway start command). Every request outcome, rejection and feedback vote is buffered in process and upserted a few seconds later inside a transaction with a 3-second `statement_timeout`; the write is fire-and-forget; a failed write increments `process.store.writeFailures` and drops that batch (its USD estimate stays in the process spend total), and the first write and first read failure per process also print one `zarvis.store` line with the error class only, so a migration that did not apply is visible in the deploy log. Rows in a batch are upserted in `day|route` order so concurrent flushes from several replicas cannot deadlock, and the latency histogram is added element-wise with `unnest … with ordinality`. Rows keep the same counters as the process metrics plus `estimated_usd` and a 9-bucket latency histogram (bounds 250 ms … 60 s, reported as `dailyLatencyBucketBoundsMs`; the endpoint adds `p50BucketUpperMs` / `p95BucketUpperMs` per row). Because rows are per route, model-route latency is no longer blended with sub-second local answers.

### Daily spend ceiling

`ZARVIS_DAILY_USD_CAP` (e.g. `25`) forbids the provider once the estimated spend for the current UTC day reaches the value: the request still goes through origin, body, concurrency and quota checks and the local pipeline (`localOnly`, the canary's zero-cost mode), so questions the public records answer directly keep working at no cost, while a question that needs the model ends with an error event explaining that today's limit for model-assisted answers was reached (log outcome `spend_cap`, counted as a rejection, no `Retry-After`; the chat stays usable). The estimate is the durable daily total (re-read from Postgres at most every 30 seconds, in the background) plus usage this process has not flushed yet, including the lower bound priced for failed answers, so it is accurate to within roughly 30 seconds across replicas. The check is evaluated before quota reservation and therefore also applies during a `ZARVIS_QUOTA_PAUSE_UNTIL` window. If the table cannot be read, or right after a restart until the first background read completes, the process falls back to what it has counted itself and keeps counting; an unpriced model answer under a cap sends the `unpriced_usage` alert. Unset or invalid means no ceiling.

### Alerts

`ZARVIS_ALERT_WEBHOOK_URL` (https; a Discord or Slack incoming webhook, or anything accepting `{"content": "...", "text": "..."}` JSON) receives at most one message per type per ten minutes per process for:

- `provider_failures`: at least three consecutive failed answers, or at least 25% failed among the last 20 (minimum sample eight; aborted answers are ignored). The message carries counts and the latest error class.
- `rejection_spike`: at least 20 quota/busy/spend-cap rejections in the last ten minutes (only the last 20 timestamps are kept, so `alerts.rejectionsLast10Min` reports at most 20).
- `spend_cap`: the daily USD ceiling was reached; model answers are declined until 00:00 UTC while direct answers continue.
- `unpriced_usage`: a cap is configured but a model answer had no price (unlisted model without rate overrides, or a missing usage report), so the cap could not count it.
- `canary`: a canary run failed, with the failed case labels.
- `failover`: the primary provider failed a request's first model call and the fallback provider answered; the message carries both provider labels and the error class.

Delivery failures are counted in `alerts.failed`. The variable is never logged or returned by any endpoint; `alerts.configured` only says whether it is set.

### Canary

`GET /api/zarvis/canary` is gated like `/api/cron/refresh`: `Authorization: Bearer $CRON_SECRET` (the existing service secret, minimum 16 characters). It runs the four zero-cost starter phrasings through the real `prepareLocal` / `generateAnswer` path with the provider forbidden (`localOnly`): the privacy FAQ (`STARTERS[0]`), the treasuries starter, `What is the ZEC price?` and `What is ZIP 317?`. Each must finish on the local route with zero model calls, non-empty text, at least one source, and, for the two data-backed cases, the live reader's source URL (absent when the feed fails, which is how the launch-day treasuries outage would have been caught). The price case also fails when its answer is the "unavailable" template: on 2026-09-29 CoinGecko began answering 403 to the production host, the reader was still cited, and the canary passed while every price on the site was missing. The quote oracle (`src/lib/pricing/live-price.ts`) now falls back to CoinPaprika and then Coinbase, and each quote names its provider. Results are stored in `zarvis_canary` and returned as JSON; a failed run answers HTTP 503 and sends the `canary` alert. With `ZARVIS_CANARY_MODEL=true` and the assistant enabled, one paid model question (`STARTERS[2]`) is added per run and counted in the metrics like any other model answer (about $0.01–0.05 per run with grok-4.7).

The ZIP case needs a fresh corpus. While the public ZIP source cannot be refreshed within its six-hour window (the build-time snapshot right after a deploy, or a GitHub rate limit), that question is still answered, by the model instead of directly, so the run reports the case as skipped (`skipped`, `skippedCases: ["zip"]`, case `skipped: "zip_corpus_stale"`) and stays `ok`. A read failure is not staleness: the case then runs and reports its error class. Three consecutive skipped runs send the `canary` alert with a "ZIP corpus stale" message, because numbered ZIP questions are then costing model calls.

Schedule: the server process runs the canary itself, like the ZCG refresh in `src/instrumentation.ts` (`src/lib/zarvis/canary-schedule.ts`): a ZIP corpus warm-up 20 seconds after boot, the first run 3 minutes after boot, then every hour; `ZARVIS_CANARY_SCHEDULE=false` disables it. Each replica runs its own schedule; rows in `zarvis_canary` are per run. This live canary is scheduled by the server itself; the shared GitHub workflow runs the automated code checks. The endpoint stays for on-demand runs; a request that arrives during a run shares that run. Manual call:

```sh
curl --fail-with-body -H "Authorization: Bearer $CRON_SECRET" https://openzcash.org/api/zarvis/canary
```
