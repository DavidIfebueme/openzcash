# ZEC Observatory

Public read-only analysis at `/zec-observatory`; `/cex-zec-dex` redirects permanently. JSON remains at `/api/markets`. Research verified September 22, 2026. The project’s source APIs are queried on the server. No credentials, chain writes, new database schema, or runtime dependencies are introduced.

## Volume benchmark

Rolling 24-hour, reported USD trading activity. The universe is **observed sources**, not every trade globally. The top bars have the same scale, CEX + DEX. DEX includes native and wrapped ZEC spot execution. NEAR Intents routing remains visible as a separate accounting layer, outside spot totals. These are heterogeneous provider measures, not an independently audited consolidated tape. Providers may estimate USD volume using current prices rather than transaction-by-transaction execution prices. Reported spot excludes perpetuals on both sides, including Hyperliquid perpetuals; only its UZEC/USDC spot book is included. Outlier filtering is not an independent wash-trading audit.

- [CoinPaprika ZEC markets](https://api.coinpaprika.com/v1/coins/zec-zcash/markets) and [exchange registry](https://api.coinpaprika.com/v1/exchanges): examine every returned row. Include spot with a verified CEX/DEX registry classification. Exclude outliers, derivatives, unknown classifications, quote timestamps older than two hours or over five minutes in the future, and duplicate exchange/base/quote keys. Prefer the newest duplicate. Coinbase USD/USDC and Gemini USD/USDC/GUSD/RLUSD aliases share one execution book and are counted once, preferring valid USD. HitBTC, Gleec, FMFW and Bequant ZEC/BTC and ZEC/USDT share matching execution records and are deduplicated across platform aliases; FMFW’s legacy USD label maps to that USDT book. These exact mappings are evidence-based, not a general assumption that stablecoin markets are identical. Match the coin ID, including ZEC as quote; do not match ticker text alone.
- [Hyperliquid spot](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint/spot): public `spotMetaAndAssetCtxs` query. Match Unit Zcash by token ID `0x1c994ad3381d31c86c8c2d74ed89a365`, symbol UZEC, and USDC quote. Join contexts by `coin` / market `name`, **not array position**: the live arrays are not aligned. `dayNtlVlm` is USDC notional, treated as USD. Other tokens with ZEC in their names are not Zcash.
- **Wrapped ZEC registry:** [Coinbase cbZEC](https://www.coinbase.com/campaigns/wrapped-assets), [NEAR / OmniBridge tokens](https://1click.chaindefuser.com/v0/tokens), [Zenrock litepaper](https://docs.zenrocklabs.io/zenrock-litepaper.pdf), [Universal contracts](https://docs.universal.xyz/docs/developers/contract-addresses), and [Binance-Peg registry](https://explorer.bnbchain.org/asset/ZEC-93E). Eleven token deployments across eight networks are pinned in `src/lib/markets/wrapped.ts`. Confirm exact contracts, not ticker/name matches. EVM addresses are normalized; Solana mints remain case sensitive.
- **Pool coverage:** [DEX Screener token-pairs](https://docs.dexscreener.com/api/reference) for every registered deployment, plus up to three pages of [GeckoTerminal token pools](https://www.geckoterminal.com/dex-api) per registered Solana, Base and BNB Chain token. Each indexer is independently validated. A working alternative remains usable if the other indexer fails, but carries an explicit partial-coverage flag through the token rows, source list and headline. Successful GeckoTerminal pages survive a later page failure. Reaching the three-page cap or DEX Screener’s observed 30-pool limit is flagged as bounded/partial coverage. Deduplicate by network and pool address across indexers **and token feeds**, including cbZEC/uZEC pairs; prefer the first source at equal retrieval time. Group execution venues by chain for the compact leaderboard, preserving venue sources in expandable rows. An empty index is unavailable coverage, not a chain-wide zero. Provider pool limits and time windows can differ; these are bounded observed markets, not a full blockchain trade audit. CoinPaprika PancakeSwap/ApeSwap/Uniswap-BSC/Orca/Raydium/Meteora duplicates are replaced by pool feeds.
- [NEAR Intents ZEC explorer](https://explorer.near-intents.org/?toTokenId=nep141%3Azec.omft.near): read the public server-rendered token-volume object as data; never execute upstream code. Validate the exact token filter, timestamp and `isStale` flag. The page's token total repeats when ZEC is selected in both filters; count it once, not once as input and again as output. It is token activity, not whole-protocol volume. The token 24h, 7d, 30d and lifetime totals are retained outside the spot benchmark. Routed activity may already execute through tracked DEXs, so it is never added to those execution venues. The homepage all-asset total is contextual, never substituted for ZEC. [NEAR confirms confidential execution](https://intents.near.org/confidential); [NEAR Revenue](https://revenue.near.org/) publishes all-asset confidential TVL, not a separate ZEC confidential trading total. Validate the latest dated TVL observation against its displayed total and reject observations older than 72 hours. TVL never enters volume. NEAR Revenue explicitly labels its figures illustrative; its TVL is labeled illustrative here too and is not treated as an independently verified quantity. Private/unreported routes are outside observable coverage. A changed HTML contract fails closed.
- [Maya Midgard](https://midgard.mayachain.info/v2/doc): explicit `from` and `to` 24 hours apart for `ZEC.ZEC`; require matching returned window, a synchronized index, and an indexed block no more than five minutes old (at most one minute ahead). Read ZEC halt/trading-pause flags separately from [MayaNode inbound addresses](https://mayanode.mayachain.info/mayachain/inbound_addresses); an available pool does not mean trading is active. USD volumes are integer cents; divide by **100**, not 1e8. Native, trade and synth activity included. Zero is valid only in a valid source response.
- [THORChain registry](https://gateway.liquify.com/chain/thorchain_midgard/v2/pools): source is the current endpoint linked by [THORChain developer documentation](https://dev.thorchain.org/). A successful full registry with no `ZEC.ZEC` reports “not listed”; it does not create a zero-volume venue. If a ZEC pool appears, load its direct window.
- [Rhea / GeckoTerminal](https://www.geckoterminal.com/near/pools/refv1-6065): direct ZEC pool execution on NEAR, validated by pool ID and exact token identity. Fresh volume enters the DEX benchmark once; matching CoinPaprika venue rows are replaced. NEAR Intents routing is not added to it.

For CEX volume C and DEX volume D:

- DEX share = D / (C + D).
- Additional DEX volume for parity at unchanged CEX = max(0, C − D).
- DEX/CEX ratio = D / C × 100; undefined when C is zero. It can exceed 100%.
- For target DEX share q, required DEX volume = C × q / (1 − q); additional activity = max(0, required DEX − D). CEX stays fixed, so combined volume changes. The displayed milestones are 10%, 25% and 50%. At parity, share is 50% and the ratio is 100%.
- Scale for parity = C / D; undefined if D is zero. **Overtake** requires D > C; equality is not success.

The definitions follow [DefiLlama spot share](https://defillama.com/dexs) and [The Block DEX/CEX ratio](https://www.theblock.co/data/decentralized-finance/dex-non-custodial/dex-to-cex-spot-trade-volume). The Block chart is monthly; this dashboard uses rolling 24h observations and does not present the two datasets as directly comparable. [DefiLlama methodology](https://docs.llama.fi/analysts/data-definitions#aggregator-volume) also separates routed/aggregator volume from execution volume. The former migration slider is removed: milestones describe required DEX growth at unchanged CEX, not a forecast of users moving between venues.

Missing feeds are not zero. Stale volume is excluded from the current comparison; remaining sources are visibly marked partial. Without either side, the comparison is unavailable. No historical trend, timeline, or forecast is fabricated from a one-day snapshot. ETF share turnover and perpetual futures are excluded from the spot benchmark.

## Balances and supply

[CipherScan API](https://cipherscan.app/docs) provides the complete label registry, rich list, individual address balances and `blockchain-info`. All labels are retained, not just the rich-list leaders; addresses absent from the top 500 are requested individually with bounded concurrency. Missing balances stay null. Addresses are deduplicated before aggregation. The rich-list `balanceZat` is zatoshis, but its `balance` is already ZEC; the individual-address `balance` is zatoshis. These contracts differ and are tested.

Coinbase hot/cold/Prime labels are grouped; likewise Binance, Gemini, Kraken and KuCoin. Grayscale's upstream category `exchange` is reclassified as fund, and Hyperunit as bridge, while the original label/category is retained per address. No beneficial owner is inferred from a custodian address. Trading venues without a matched label have no inferred custody balance. Shielded owners and unlabeled wallets cannot be assigned to exchanges. Totals are visible minimums, not proof of solvency or complete reserves.

Rich-list labels are merged by exact address with the complete registry, so newly published labels can appear even before the registry catches up. The registry takes precedence on conflicts; missing verification flags are never upgraded to verified. The **Whales** tab shows individual transparent addresses with at least 10,000 ZEC among the top 500 scanned. This is a size filter, not an owner classification; unlabeled addresses remain unidentified. They do not enter CEX balances or imply distinct beneficial owners. Repeated addresses count once; conflicting balances reject the snapshot.

Explicit public attributions can supplement an unlabeled address. They retain the publisher, source URL and report date, are always marked **public attribution**, and never receive a CipherScan verification flag or replace an upstream label. The September 19, 2026 [Ember report](https://www.binance.com/en/square/post/368329271524964) names Garrett Jin and publishes `t1gGCYpyURMo2FcYDSqeR8pgp2Kx9rnT72V`. Its balance is read from CipherScan (202,076.207 ZEC when checked September 22), not the report's rounded 202,077 figure. This is a sourced public attribution, not cryptographic proof of ownership or an inference from shielded flows.

**All holders** combines address evidence with issuer disclosures, one row per entity. Grayscale, Cypherpunk and 21shares show the same dated positions as their fund cards. If an entity also has labeled addresses, those remain available inside its row as a separately scoped view; they are not added to the issuer's position. The address-only CEX totals are unchanged by issuer disclosures. Positions across entities may overlap through custody, so this combined list has no additive total. The initial view is All holders; category filters and the nine-row pagination remain available.

The [Ironwood tracker](https://cipherscan.app/ironwood) is linked from supply methodology. Its flow chart's `Coinbase` denotes block rewards (the mining category), not Coinbase exchange custody. No exchange ownership is inferred from that flow.

Supply denominator is the mainnet node's **on-chain chainSupply**, including lockbox. Validate node synchronization and reconcile the integer-zatoshi sum of every value pool exactly, including Ironwood, against chainSupply. Retain block height/hash. This is internal reconciliation of a node response, not independent auditing. A 21M maximum is never substituted for current issued supply. Source snapshots can differ by a few blocks. If mapped balances exceed the transparent pool, hide their supply percentages rather than display impossible shares.

## Represented supply

cbZEC on Base is pinned to Coinbase's `0xB2000000000000000000008501b13360000cb2EC`. Base cbZEC/uZEC and BNB Binance-Peg supply use read-only RPC: validate chain ID, pin `totalSupply()` and `decimals()` calls to the same block, then convert integer token units. Solana uses actual mint decimals and finalized slots. A supplied amount above the native 21M maximum is rejected. Retain the observation block and date. Other networks retain their registry/market rows with supply unavailable until a verified reader exists.

Represented supply is **not added** to native ZEC or exchange custody, and a valid mint/supply response is **not proof of backing**. Kamino collateral similarly remains a use of existing token supply.

## Refresh behavior

Market/supply sources: five-minute server cache. Addresses, represented token supply and Kamino: ten minutes. Issuer disclosures and confidential TVL: one hour; their reporting dates remain visible. The page auto-checks every five minutes while visible and provides a refresh button. A server cache hit does not refresh its successful timestamp. Failed requests back off for a minute, retain prior data explicitly as saved, and never replace missing data with zeros. Source availability and exclusions are inspectable on the page and in JSON.

## Pool liquidity

The expanded DEX rows display the sum of reported pool reserves in USD across unique pools (DEX Screener `liquidity.usd`; GeckoTerminal `reserve_in_usd`). This values both assets, including wrapped ZEC and the other asset. It is not ZEC-only holdings, 24-hour volume, circulating supply, CMC’s CEX liquidity score, or guaranteed executable depth; concentrated liquidity can be outside the current trading range. Missing pool liquidity makes the venue liquidity unavailable instead of adding fabricated zeros. Uniswap and PancakeSwap versions are grouped by protocol and network after exact pool deduplication.

## Snapshot consistency and refresh

The server-rendered page, `/api/markets` and startup collector share one versioned, process-wide dashboard reader. A collection publishes atomically, and `generatedAt` identifies that collection rather than the time of each HTTP request. The header shows the published snapshot time in UTC. A full reload therefore cannot independently return a different cached source set from the refresh button.

The single-instance Railway service warms public market data at startup and checks for due work every minute. Normal snapshots refresh after five minutes; failed volume sources retry after a bounded delay. Page navigation serves the dated snapshot immediately during collection; the refresh endpoint joins that same collection. Source-level timestamps, partial coverage and unavailable fields remain explicit. A provider failure can change observed coverage and the next percentage; it is not evidence that trading activity itself fell. No older source value is silently reclassified as fresh. Cold startup still needs one initial collection. Multiple server instances would require a shared external snapshot store.
