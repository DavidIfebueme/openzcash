Direction confirmed on 2026-11-10: maintain OpenZcash as open-source community infrastructure, supported by voluntary donations and contributions. Revised on 2026-11-12: OpenZcash will not apply for a grant for itself, neither to ZCG nor to the Coinholder retroactive grants; the open letter says so.

## State of the treasury

On 2026-11-10 the owner supplied the dedicated mainnet donation address and full viewing key for public disclosure. These intentionally public details live in `src/lib/openzcash-treasury/account.ts`; they are not spending credentials. The QR is generated locally from that exact address using the existing `qrcode` dependency, with no amount, memo or external QR service. The address and full key can be copied; the QR can be downloaded as PNG. Clipboard failure is reported; the address and the key are always shown whole, so either can be selected by hand.

The owner identified Vizor as the source wallet. Local ZIP 316 encoding checks validated both Bech32m checksums, F4Jumble padding and item lengths. The address includes an Orchard receiver; the full viewing key includes transparent, Sapling and Orchard items. These encoding checks do not prove account-to-address derivation or a synchronized balance. The generated PNG was independently decoded with jsQR and matched all 106 characters of the supplied address.

The owner confirmed the account was created in Vizor on 2026-11-10. A dedicated local ZKool engine imports only the published full viewing key. The worker checks that its exported full viewing key and Orchard donation address match the public configuration. It chooses a scan start before the creation day, verifies that block's timestamp through TLS lightwalletd, waits for synchronization with transaction details, and reconciles the complete net history against the engine's confirmed balance before publishing a snapshot.

## Read-only synchronization

Engine baseline: [ZKool 6.36.0](https://github.com/hhanh00/zkool2/releases/tag/zkool-v6.36.0), commit `4d12780960392d87b850ddaf677c49ee058f538e`, compiled with `cargo build --locked --release --bin zkool_graphql --no-default-features --features graphql,ledger --manifest-path rust/Cargo.toml` from the upstream repository root. This is a separate dependency, not part of the web application's npm build.

Start the compiled engine with a dedicated database and loopback binding:

```sh
zkool_graphql --db-path /path/to/treasury.db --lwd-url https://zec.rocks \
  --port 18232 --bind-address 127.0.0.1 --coin 0 \
  --allow-unauthenticated --allow-unencrypted-database --no-mempool
```

These flags are for a local engine containing only the expressly public viewing key. Do not expose its GraphQL port to the network or reuse a database that contains spending keys. The web app exposes only its validated read-only snapshot. On macOS, `XDG_DATA_HOME` can keep the engine's downloaded Sapling parameters in the same dedicated runtime directory.


- `scripts/sync-openzcash-treasury.ts` is an operator CLI, separate from the Next.js application. `npm run treasury:sync` performs one scan; `npm run treasury:sync -- --watch` repeats every 30 seconds.
- `OPENZCASH_TREASURY_ENGINE_URL` defaults to `http://127.0.0.1:18232/graphql` and must be a dedicated loopback service. It must contain only this public watch-only account. Do not point it at a personal wallet database.
- `OPENZCASH_TREASURY_INDEXER` defaults to `https://zec.rocks`. The engine and worker must use the same mainnet indexer.
- `OPENZCASH_TREASURY_BIRTHDAY_HEIGHT` can pin an earlier starting height. Its block timestamp must precede the owner-confirmed creation day with a one-day margin. Without an override, the worker starts 10,000 blocks below the current tip and steps backward if necessary.
- `OPENZCASH_TREASURY_SNAPSHOT_PATH` defaults to `.cache/openzcash-treasury/snapshot.json`. The worker writes atomic replacements. Engine databases, lock files and the worker's live snapshot are local runtime data and must not be committed; the one snapshot kept in the repository is the published one described below. The web process only needs read permission for the snapshot.
- The worker takes `sync.lock` beside the snapshot before it writes anything and refuses to start while another worker holds it; the message names the holder's PID, host and heartbeat age. The file holds the worker's PID, a token unique to that start and the host name; its modification time is the heartbeat, refreshed before and after each engine synchronization. A lock left behind by a killed worker (out of memory, `SIGKILL`, host restart) is recovered on a later start, with no file to delete by hand. On the host that wrote it, recovery is immediate when the recorded process no longer exists or when the lock records the starting worker's own PID, because a restarted container hands out the same PIDs. In every other case recovery waits until the heartbeat is older than 25 minutes, the 20-minute synchronization timeout plus a margin: a PID that passed to an unrelated process, a lock without a readable PID, a lock written on another host (a new container, or one sharing the directory) and a lock in the earlier PID-only format. That wait is the longest the treasury stays stale after a kill. Recovery is exclusive: a worker first takes `sync.lock.recovery` and inspects the lock again while holding it, so when several workers start together on an abandoned lock one is accepted and the others are refused. A `sync.lock.recovery` older than 60 seconds, left by a worker killed in the middle of a recovery, is cleared on the next start. A worker that finds its lock replaced or removed at a heartbeat stops without publishing; the heartbeat is also checked before a failure is recorded. A worker started from code older than this lock never refreshes it, so stop it before starting a newer one. The logic lives in `src/lib/openzcash-treasury/sync-lock.ts`.
- `data/openzcash-treasury/snapshot.json` is the published snapshot: a copy of a snapshot the worker produced, committed so that the public page has a verified balance when no live reading exists. The page and the API present it as the last known balance, with its block and UTC time, never as live: the status is `stale`, or `error` while a live update is failing. A live reading replaces it as soon as it is at least as recent, that is, synchronized to the same block or a later one. It goes through the same validation as the live file, and `src/lib/openzcash-treasury/store.test.ts` checks the committed file. To publish a newer one, run `npm run treasury:sync` against a local engine and copy the resulting `snapshot.json` over it in a pull request. Decision of the owner on 2026-11-12; until then no snapshot was committed. The first one was produced that day at block 3,564,637, with the locally compiled ZKool 6.36.0 and `https://zec.rocks`.
- `GET /api/openzcash-treasury` serves the validated snapshot with `Cache-Control: no-store`. No request imports a key or starts a scan. Legacy key-import, admin and scanner HTTP routes stay retired.
- The page refreshes the read-only feed every 15 seconds. It shows the synchronized block and UTC timestamp. After two minutes without a successful scan, it labels the data as the last known balance; errors retain the previous verified snapshot. Missing, invalid or wrong-account data remains unavailable, never zero.

Amounts are exact integer zatoshis. Received and Spent are positive and negative **net account movements**, with outgoing fees included. Change and transfers between pools are not counted twice. A zero-net transfer stays in All as Internal and retains recoverable memos. Every published snapshot must satisfy `received - spent = confirmed balance`. Only confirmed transactions appear; an unconfirmed test donation appears after mining and the next successful scan.

Memos come from the engine's decrypted external notes and outgoing outputs. Blank/non-text memos are absent; multiple recovered text memos remain distinct. The UI renders plain text, never memo HTML. A full viewing key cannot recover outgoing data encrypted with an unrelated/randomized outgoing key. This integration cannot manufacture a missing memo.

Coverage follows the account's shielded keys and the engine's stored transparent addresses; it is not an exhaustive search of all possible transparent child indexes. The published donation address is Orchard-only. Expense purposes and receipts can be added as separate records; the viewing key does not prove off-chain expense claims or the absence of other wallets.

The scanner is a separate process, never part of the web application: the site only reads the snapshot. It can run on any host beside the engine, sharing the snapshot read-only with the web process. For production the owner chose to run it inside the web service's own container, described in the next section; it has been running there since 2026-11-12. Whenever that runtime is off, the public page shows the published snapshot as the last known balance. A local preview is not evidence of a public deployment.

## Production runtime (inside the web service)

Decision, 2026-11-12: the owner chose to run the wallet engine and the worker in the portal's own Railway service, on a volume, instead of a dedicated service or the separate worker host. The code is in `scripts/treasury-runtime.ts` and `src/lib/openzcash-treasury/runtime.ts`. It was enabled on the production service on 2026-11-12 at 14:59 UTC, and the owner decided that day to keep it there for now; a dedicated service remains an option, not a plan.

- The start command in `railway.toml` ends by replacing the shell with `npm run start`, so the site is the process the platform signals. Only when the service sets `OPENZCASH_TREASURY_RUNTIME=enabled` does it first start the runtime in the background; with any other value, or none, no runtime process exists and the service behaves as before. The site's start, health check and restart policy do not wait on the runtime, and a runtime that fails or exits does not stop the site. `src/lib/openzcash-treasury/start-command.test.ts` runs that exact line.
- `OPENZCASH_TREASURY_SNAPSHOT_PATH` must be an absolute path on the service's volume, outside the application directory, for example `/data/openzcash-treasury/snapshot.json` with the volume mounted at `/data`. Its directory becomes the runtime directory: `snapshot.json`, `sync.lock`, `engine/` (database and Sapling parameters) and `bin/` (engine binary). The same variable tells the site where to read.
- On start the runtime refuses to continue if something already listens on the engine port, which means another runtime is running in the container. It then removes the lock files and unfinished snapshot writes left by the previous container, starts the engine on loopback with the flags above, waits up to a minute for its port and starts the worker with `--watch`. Removing the leftovers is safe here and only here: a Railway volume is mounted by one deployment at a time, and no worker of the new container has started yet.
- The engine and the worker are restarted whenever they exit, after a pause that doubles from one second to one minute and starts over after a minute of healthy running. A runtime that stops with `runtime stopped: …`, for example on a volume it cannot write, is not started again until the next deploy.
- A container stop signals only the site's process; the runtime, the engine and the worker end with the container, without cleanup. That is why the leftovers are cleared at the next start. When the runtime itself receives `SIGTERM`, it stops both processes and the worker releases its lock.
- Engine binary: the runtime downloads the `zkool_graphql` file that the ZKool project's release workflow attached to release `zkool-v6.36.0` (Linux x86_64, built with `graphql,bundled-sapling-params,ledger`) and runs it only when its size and SHA-256 match the values pinned in `TREASURY_ENGINE`. The digest is the one GitHub publishes for that asset. The file is installed read-only and its digest is checked again before every start of the engine. This is the upstream build, not the locally compiled baseline above. To run a binary you built yourself, put it on the volume and set `OPENZCASH_TREASURY_ENGINE_BIN` to its absolute path; then nothing is downloaded and nothing is checked.
- The engine is a third-party program. When the runtime starts as root, it runs the engine as the unprivileged account 65534 (`nobody`), which owns only `engine/`: it cannot read the site's process, the service's variables or the snapshot. When the runtime is not root it cannot change accounts, says so in the log, and the engine runs as the site's user.
- The engine and the worker are started with only `PATH`, the locale, time-zone and certificate variables, and the `OPENZCASH_TREASURY_*` settings. That keeps the service's database URL and provider keys out of their environment and logs; it is not a sandbox. The worker is this repository's code and runs as the site's user.
- `OPENZCASH_TREASURY_ENGINE_URL`, when set, needs a port of its own: 1024 or higher and different from the site's `PORT`. Do not point the retired `ZKOOL_GRAPHQL_URL` at the treasury engine.
- `tsx` is a production dependency because the runtime and the worker run from the TypeScript sources.

Costs of this choice: a Railway service with a volume has a short downtime on every redeploy and cannot use replicas. Measured on 2026-11-12 with a probe every few seconds: attaching the volume took the site down for about three minutes, because the platform removed the running deployment before the new one had built; the redeploy that followed kept the old deployment serving during the build and dropped requests for 10 to 15 seconds at the switch. A deploy triggered by a merge to `main` behaved the same way later that day: about four minutes of build with the old deployment serving, then between 13 and 19 seconds of failed requests at the switch, after which the API answered `"status":"synced"` at once because the snapshot on the volume was still fresh. The engine and the worker use the site's memory and processor; if the container runs out of memory the platform restarts the whole service, site included. The engine's unauthenticated GraphQL port, loopback only, is reachable by any code running inside the site's container. The engine holds only the public viewing key.

Verified on 2026-11-12, on macOS, not as root, with the locally compiled engine: a first synchronization from an empty directory, recovery after the worker and the engine were each killed, a restart over the lock of a killed runtime, the refusal of a second runtime, and a stop on `SIGTERM`.

Verified in production on 2026-11-12, from the log of the first deployment with the runtime enabled: the pinned release binary was downloaded and its digest verified on the Railway image, the engine listened on `127.0.0.1:18232`, the worker verified the public viewing key and donation address and synchronized block 3,565,740, and `GET /api/openzcash-treasury` answered `"status":"synced"`. That log has no `not running as root` line, so the runtime handed the engine to the unprivileged account; this was read from the log, not confirmed from inside the container. Not measured: the memory the engine and the worker use beside the site.

### Enabling it

These steps were carried out on the production service on 2026-11-12; they stay here as the procedure for another environment. Each step is the owner's to take.

1. Deploy this code with no new variables. No runtime process is started and the site is unchanged.
2. Attach a volume to the web service, mounted at `/data`. From this point every redeploy has a short downtime.
3. Set `OPENZCASH_TREASURY_SNAPSHOT_PATH=/data/openzcash-treasury/snapshot.json` and `OPENZCASH_TREASURY_RUNTIME=enabled`, then redeploy.
4. In the deploy log expect, in order, `[treasury] engine binary downloaded, digest verified`, `Listening on 127.0.0.1:18232`, `Verified public viewing key and donation address` and `Synced block …`. The engine's own `Listening on` line shows the address it bound; it must be `127.0.0.1`. `GET /api/openzcash-treasury` then answers with `"status":"synced"`.
5. To turn it off, remove `OPENZCASH_TREASURY_RUNTIME` and redeploy. While the snapshot path stays set, the page keeps the last snapshot, labelled as the last known balance.

If the log repeats `engine could not start` or `engine exited`, the site keeps running in its previous state. On a new image the likely causes are a missing system library, which the engine's own error line names, or a platform that does not let the runtime change accounts.

Viewing-key terminology: [ZIP 316](https://zips.z.cash/zip-0316#terminology). Public viewing keys can expose transaction details and memos; they do not authorize spending.

## Source release and contributor incentives
