# Automatic official-source revisions and mainnet anchoring

Run the scheduler separately from the public web process. It uses PostgreSQL for the durable queue and an operator-managed wallet transport for optional chain writes. See [Deployment](deployment.md).

New automatic anchors require an explicitly configured **Ironwood** destination and an Ironwood acknowledgment from the isolated signer. Missing pool configuration is legacy Sapling for reading only and cannot authorize an automated spend. This code requirement is separate from live deployment and successful on-chain acceptance. Existing Sapling archives remain verifiable and must not be republished merely to change pools. Follow the [Ironwood cutover](participate-ironwood-cutover.md) before restarting a worker with a changed receiver.

## Automatic flow

The timer starts a worker cycle 60 seconds after the previous cycle finishes. Its database checkpoint limits official-source discovery to once every five minutes, with serial bounded pagination, a ten-minute overlap, rate-limit backoff and the fixed `ZcashCommunityGrants/zcashcommunitygrants` repository. Discovery reads open and closed issues. **New applications** must be open with no terminal status. They qualify either through the official application and ready-for-review labels, or through populated application-owner, requested-USD, summary and description fields from the grant form, even with a custom title and no labels. The latter path imports applications before committee triage; it does not invent official labels or a committee decision. V12 credit applications, generic issues, pull requests and public Participate submissions remain excluded. **Already archived official applications** continue tracking approval, rejection, withdrawal, closure, reopening and label changes.

The activation timestamp remains the lower bound for discovering unknown applications. A separate bounded reconciliation revisits known archives, including the five explicitly mapped historical records, without importing unrelated old issues. With a read-only GitHub token it checks at most two due known sources per discovery cycle; without a token it checks at most one per fifteen minutes. Only records last checked over an hour ago, or never checked by this scanner, are due. These are queue limits, not a promise that every record is reconciled in an hour. This slower path also detects associated comment edits or deletions that do not update the issue timestamp.

Each new application or changed official observation follows this path without manual approval per revision:

1. Fetch the complete bounded source evidence and reread the issue to reject a mixed capture. Freeze the exact current Markdown, source metadata, original label names/colors, relevant GitHub events and repository-associated comments in a V2 source package.
2. Compare the observation against the latest durable predecessor. If it changed, append a revision with the previous manifest hash and its own immutable job. Initial applications are under review; later outcomes are dated official-source observations, not new Participate committee votes. No demo Zcred are charged.
3. Import up to ten due captures, independently of wallet availability. Group up to ten imported, uncommitted revisions into one Merkle tree. In one database transaction, freeze every individual inclusion proof and link every job to its anchor. Persist the dispatch intent for the whole batch before contacting the signer.
4. The node independently reconstructs the root from the sorted, unique manifest hashes and checks the memo count, network, sync state, dedicated wallet, pinned receiver, transaction structure, fee and daily record budget. It proves, signs and broadcasts one transaction for the batch.
5. A separate view-only reader and Zebra verify the exact memo and canonical block. Every member receives the common transaction reference and its own inclusion proof. All receipts become verified at ten confirmations. Later failures supersede earlier verification observations without deleting receipts.

The isolated wallet also requires ten confirmations before spending an incoming or change note. A funded wallet with a single spendable note can therefore process anchors sequentially: each send consumes that note and its change becomes available after confirmation. After an explicit insufficient-balance rejection, the signer reads only its pinned account's Ironwood balance. If the spendable balance is zero and pending funds cover even the maximum permitted fee plus the archive output, it reports `WALLET_AWAITING_CONFIRMATIONS`. The queue logs `anchor_waiting_for_confirmations` and rechecks after one minute, without exponential funding backoff, replacing the signing intent or reducing confirmations. A failed or inconclusive balance read retains `WALLET_INSUFFICIENT_FUNDS`; uncertain creation/signing/extraction still requires reconciliation.

Each worker cycle processes at most one frozen batch of up to ten revisions, including new proposals and official-source updates. A batch closes from the due, imported records available in that cycle; it does not wait to fill ten slots. New arrivals cannot join a prepared or dispatched batch. Retries, lost responses and process restarts recover exactly the same members and root. Existing single-record commitments and historical transactions are preserved. The fee is recorded once on the first manifest in canonical order, while every member shares the transaction ID. A ten-record batch therefore pays one transaction fee, not ten fees.

Activity batches are also implemented in `lib/services/activity-automation.ts` and enabled separately through `activityEnabled`. They use their own immutable inventory and inclusion proofs; see [Activity](participate-activity.md).

The full files remain in the application archive and are recoverable through the existing package/receipt downloads and standalone verifier. The chain commits to their hash; linked external attachments and forum discussions are not copied by this job. Previous revision bytes, manifests and receipts remain unchanged. Legacy V1, review snapshots and historical summaries remain readable; changing format alone does not republish them. See [official source revisions](participate-source-revisions.md) for the evidence boundaries, migration and acceptance checks. That document describes implemented behavior separately from deployment and confirmed-chain evidence.

An official proposal package preserves its complete captured Markdown, author/source metadata, requested amount and captured categories/labels, source status/events and repository-associated comments, file hashes, capture time and predecessor manifest hash. Participate member likes and comments are a separate activity record; grouping official revisions does not silently add that activity, a committee vote, later spreadsheet changes or uncopied attachments to the immutable source package.

Import happens before the signer call, so normal member comments and likes are available while the Ironwood transaction is pending. Initial discovery is normally within five minutes; the serial worker, source backoff and chain confirmations can add time. Targeted recovery of applications missed by an older intake rule is `captureSelectedOfficialProposals` in `lib/services/participate-source-revisions.ts`; this distribution ships no command for it. It captures at most ten explicit official issues through the same validation and never calls the signer; the normal worker then imports and anchors them.

The public board refreshes the shared listing and imported participation records every 60 seconds while visible, without interrupting a focused editor or a like request. Applicant category and descriptive metadata are carried from the initial GitHub read; committee labels and published verdicts retain their own provenance. Normal latency is the five-minute discovery interval plus processing and the next board refresh; rate limits and upstream failures can extend it. Import and discussion access never wait for the daily signer budget.

Skipped new issues emit `source_candidate_skipped` with a controlled reason code. Targeted recovery emits `source_target_intake_completed` or `source_target_intake_failed`; malformed captures and failed fetches retain the existing error logs and retry behavior.

## Failure and spending behavior

- PostgreSQL holds a worker lock. The signer also holds a node-side file lock.
- Each host, issue number and revision identifies one immutable job. The previous manifest hash links the complete revision chain. The same Merkle root belongs to one durable PCZT journal; a later source change does not replace an uncertain earlier signing intent.
- Observation fingerprints exclude capture time, issue timestamp alone, title/body-only edits and ordinary public replies. They include source state/reason, exact labels, status events and repository-associated comments. Comparison is against the latest observation, not a global set, so A → B → A remains a new revision. One poll can preserve several source events in a single observation.
- A malformed new candidate is quarantined with a controlled log code while other valid candidates continue. Failures while capturing a known source or fetching complete evidence retain the discovery cursor for retry; independent valid captures can still commit. Partial evidence is never sent to the signer. Rate limiting or an unavailable upstream stops further upstream requests and schedules backoff.
- Rate limits, node sync delays, connection errors and budget limits wait with backoff. Explicit insufficient-funds rejections wait for funding.
- Lost broadcast responses reconcile the saved txid, or rebroadcast **the same signed bytes**. They never select new notes or create a replacement transaction.
- Unknown creation/signing/extraction outcomes, changed policy or the signer's journal expiry guard stop with `NEEDS_REVIEW`. Resolving these requires inspecting the existing journal; do not reset the job or remove its journal to force a retry. A reader's stale `expired` status is handled separately: positive canonical node inclusion can verify the existing transaction; unavailable inclusion returns retryable `READER_SYNCING`. See the [cutover refusal semantics](participate-ironwood-cutover.md#existing-automated-transactions).
- Each new transaction has a maximum fee of **50,000 zatoshis (0.0005 ZEC)** and sends **one zatoshi** to the pinned archive receiver. The node reserves at most **ten records per UTC day**, including uncertain attempts, with one to ten records per transaction. Existing single-record budget entries count as one record. The maximum daily fee/output reservation remains **500,010 zatoshis (0.00500010 ZEC)**; batching does not expand the authorized record or spending limits. These limits are enforced on the node, not accepted from the caller. A frozen batch that exceeds the day's remaining record allowance waits for a later day without changing its membership.
